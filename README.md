# Harborside — a self-healing Bruin data platform

This repo is a **reference project**: what a Bruin codebase looks like when it is
set up so an AI agent (local or Bruin Cloud) can diagnose a broken pipeline, test
a fix outside production, and verify the result. It is the "ideal end state" the
[Build a Self-Healing Pipeline Agent](https://getbruin.com/learn/self-healing-data-pipeline-agent/)
guide works toward, made concrete across four pipelines.

Everything belongs to a fictional DTC home-goods brand, **Harborside**. The data
is generated by deterministic fixtures, so the repo is meant to be **read and
validated, not run against a live warehouse** — `bruin validate` may warn about
unmaterialized sources, and that is expected.

> The point of the repo is the **context layer**. An error message tells you a
> check failed; it doesn't tell you what the table is for, which inputs built it,
> who owns it, or how to test a fix. Those live here, in files an agent can read.

## The four pipelines

| Pipeline | Domain | Source | What it answers |
|---|---|---|---|
| [`iot`](iot/README.md) | operations | sensor gateways (Python fixture + CSV seed) | Are fulfillment-center storage conditions safe? |
| [`shop`](shop/README.md) | commerce / finance | orders + products (Python fixture) | One-time storefront revenue |
| [`webevents`](webevents/README.md) | marketing | pageview stream (Python fixture) | Web traffic and conversion |
| [`stripe`](stripe/README.md) | finance | Stripe via ingestr | Home Box subscription (recurring) revenue |

Each pipeline is a `raw → stage → report` chain, with schemas named
`<pipeline>_<layer>`:

- **raw** — source-faithful ingestion. Append-only; bad values are kept, not fixed.
- **stage** — cleaned, deduplicated, conformed, typed. The stable interface.
- **report** — business marts and aggregates that people actually query.

## Cross-pipeline lineage

The pipelines are wired together so lineage crosses boundaries — the case that is
hardest to diagnose without declared dependencies:

```
iot_raw.sensor_readings ─► iot_stage ─► iot_report.sensor_health_daily
iot_raw.sensor_registry ····(symbolic)··············▲

shop_raw.orders   ─► shop_stage.orders_clean ─┬─► shop_report.orders_daily
shop_raw.products ─► shop_stage.products_clean ┴─► shop_report.revenue_daily
                                               └─► shop_report.subscriber_revenue_daily ◄─┐
stripe_raw ─► stripe_stage.subscriptions ──(external URI, blocking)───────────────────────┘

webevents_raw ─► webevents_stage ─► webevents_report.traffic_conversion_daily
shop_stage.orders_clean ──(external URI, symbolic / non-blocking)──────────────▲
```

## The context layer

| Where | What it holds |
|---|---|
| [`AGENTS.md`](AGENTS.md) | How to work here, the company, the asset standard, and the **self-healing policy** (scope / do-without-asking / ask-first / never) |
| [`glossary.yml`](glossary.yml) | The **semantic layer**: shared entities and attributes that columns `extends:` |
| `<pipeline>/README.md` | Why each pipeline exists, why it is shaped that way, its lineage, and its designed incidents |
| `.agents/skills/` | Installed Bruin **agent skills** (`bruin ai skills all`), customized with Harborside scope |
| asset files | Owners, descriptions, tags, domains, meta, checks, unit tests — the metadata an agent reads first |

## Metadata & context feature reference

A generic reference for the Bruin metadata and context features that make a
project self-healable — what each one is, independent of this repo.

| Category | Feature/function | Description |
|---|---|---|
| Repo context | Root `README.md` | Project overview: purpose, architecture, how the pipelines fit together, and setup |
| Repo context | `AGENTS.md` | How to work in the repo — conventions, company context, asset standards, and the agent's operating policy |
| Repo context | `glossary.yml` | Semantic layer defining shared business domains, entities, and attributes |
| Repo context | Pipeline `README.md` | Why a pipeline exists and why it is shaped that way — context that can't be derived from the code |
| Repo context | Agent skills (`.agents/skills/`) | Reusable, structured instruction files an agent loads for a matching task |
| Pipeline meta | `name` / `schedule` / `start_date` / `catchup` | Pipeline identity, run cadence, and backfill behavior |
| Pipeline meta | `retries` | Default retry attempts for failed assets |
| Pipeline meta | `tags` / `domains` / `meta` | Pipeline-level labels and arbitrary key/value annotations for filtering and governance |
| Pipeline meta | `metadata_push` | Publishes asset/column descriptions to the warehouse's native metadata |
| Pipeline meta | `notifications` | Success/failure alerts to Slack, Teams, Discord, email, or webhook |
| Pipeline meta | `default_connections` / `default` | Connection and asset-default settings inherited by every asset |
| Pipeline meta | `variables` | Typed, JSON-schema-validated parameters referenced in SQL as `{{ var.x }}` |
| Asset meta | `owner` | The person accountable for the asset |
| Asset meta | `description` | What the asset is and what one row represents |
| Asset meta | `tags` | Labels for filtering assets (e.g. by layer, tier, or team) |
| Asset meta | `domains` | The business domain an asset belongs to |
| Asset meta | `meta` | Arbitrary key/value metadata an agent can filter and group on |
| Asset meta | `uri` | A stable, unique address that lets other pipelines depend on the asset |
| Asset meta | `interval_modifiers` | Shifts a run's data interval to account for late-arriving sources |
| Asset meta | `parameters` | Source/loader configuration for ingestion and seed assets |
| Column meta | `type` | Column data type |
| Column meta | `description` | The meaning of the column |
| Column meta | `primary_key` | Marks the columns that define the table's grain |
| Column meta | `nullable` | Whether the column may contain nulls |
| Column meta | `foreign_key` | Declares a reference to a parent table/column |
| Column meta | `extends` | Inherits a column's type and description from the glossary |
| Lineage | Regular dependency | A by-name upstream dependency that controls execution order |
| Lineage | Symbolic dependency | An edge shown in lineage that does not gate execution |
| Lineage | External URI dependency (blocking) | A cross-pipeline/cross-repo dependency that waits for the upstream to cover the interval |
| Lineage | External URI dependency (symbolic) | A cross-pipeline dependency visible in lineage but non-blocking |
| Governance | Column checks | Built-in data-quality rules on a column (not_null, unique, positive, non_negative, min, max, accepted_values, pattern, relationships) |
| Governance | `custom_checks` | Arbitrary SQL assertions comparing a query result to an expected value or row count, blocking or non-blocking |
| Governance | `unit_tests` | Tests that run an asset on mocked inputs and assert the expected output |
| Materialization | `create+replace` | Rebuilds the whole table each run |
| Materialization | `merge` + `incremental_key` | Upserts rows on a key for incremental loads |
| Materialization | `append` + `incremental_key` | Adds new rows for the run's interval to an append-only table |
| Materialization | `delete+insert` | Replaces only the rows in the run's interval, preserving history |
| Materialization | `partition_by` / `cluster_by` | Physical table layout for query performance and cost |
| Other | Seed asset | A table loaded from a checked-in file (CSV, Parquet, JSON, etc.) |
| Other | Dashboard | A code-defined dashboard built on the reporting layer |

## Designed incidents (the self-heal demo)

Each Python fixture also seeds realistic failures so the repo doubles as a
practice ground. The raw generators emulate the source; the thing an agent fixes
is always the `stage`/`report` SQL, a check, or the metadata — never the
generator. Each pipeline README lists its incidents, the signal, and the expected
classification. In short:

- **iot** — impossible sensor values, observed type drift, late-arriving data.
- **shop** — duplicate keys, a country-driven revenue anomaly, a product-column
  rename, a source stall, and a missed cross-pipeline (stripe) interval.
- **webevents** — a traffic spike, a new browser segment, a multi-day source gap.
- **stripe** — the well-behaved finance pipeline; the upstream in the
  cross-pipeline missed-interval scenario.

## Using the repo

```bash
# validate the whole project (the check you run on every PR)
bruin validate .

# read lineage for any asset, including cross-pipeline edges
bruin lineage ./shop/assets/report/subscriber_revenue_daily.sql --full

# run a unit test (needs a git repo + a configured connection)
bruin unit-test ./shop/assets/report/revenue_daily.sql

# (re)install / update the agent skills
bruin ai skills all
```

### Connections

Configure two connections in a repo-root `.bruin.yml` (kept out of git). Names
match what the assets declare — `gcp-default` and `stripe-default`:

```yaml
default_environment: default
environments:
  default:
    connections:
      google_cloud_platform:
        - name: gcp-default
          project_id: harborside-analytics
          location: US
          use_application_default_credentials: true
      stripe:
        - name: stripe-default
          api_key: ${STRIPE_API_KEY}
  # A safe, write-isolated environment for the agent (see AGENTS.md self-heal policy).
  agent-dev:
    schema_prefix: agent_dev_
    connections:
      google_cloud_platform:
        - name: gcp-default
          project_id: harborside-analytics
          location: US
          use_application_default_credentials: true
```

> Everything here is fictional demo context. Swap the names, owners, and rules for
> a real deployment.
